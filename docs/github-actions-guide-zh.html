CI/CD · YAML · GitHub-hosted runner

GitHub Actions 入門手冊

把「編譯、測試、打包」交給 GitHub 的雲端機器自動執行。你的電腦不用裝任何 toolchain，也能產出 Windows、Linux、macOS 的執行檔。

重點
  • 在 repo 放一個 .github/workflows/xxx.yml，寫好「什麼時候觸發、在哪種機器上、跑哪些指令」。
  • 每次 git push，GitHub 就開一台全新的 VM 照著跑，跑完 VM 銷毀。
  • 結果（成功/失敗、完整 log、產出檔）在 repo 的 Actions 分頁查看與下載。
  • public repo 使用 GitHub 提供的標準機器免費。

它是什麼

GitHub Actions 是 GitHub 內建的 CI/CD（Continuous Integration / Continuous Delivery）服務。概念上就是一台「聽到 git 事件就自動執行 shell script 的遠端機器」。

對照你熟悉的做法：以前可能在一台 build server 上用 cron 加 bash 定時拉 code、跑 make、把 image 放到某個目錄。GitHub Actions 把這整套搬到雲端，而且機器不用自己維護、每次都是乾淨環境、log 和產出檔自動保存。

能做什麼

自動 build + test每次 push 都編譯並跑 unit test，壞掉立刻知道是哪個 commit
跨平台編譯沒有 Windows 或 Mac，也能產出對應平台的執行檔
PR 檢查Pull Request 沒通過 build/test 就標紅，避免壞 code 進主線
自動發佈 release打 git tag 就自動 build 並建立 GitHub Release，附上 binary
排程工作nightly build、每週檢查相依套件更新
程式碼檢查clang-format、cppcheck、shellcheck、靜態分析
Cross-compile在 x86 runner 上用 aarch64/arm toolchain 交叉編譯，再用 QEMU 跑測試
硬體測試（HIL）把接著開發板的機器註冊成 self-hosted runner，push 後自動燒錄並測試

核心術語

由大到小：一個 Workflow 由 Event 觸發，裡面有一或多個 Job，每個 Job 在一台 Runner 上依序執行多個 Step。

術語意思類比
Workflow一個自動化流程，即 .github/workflows/ 下的一個 YAML 檔。一個 repo 可以有多個一支完整的 build script
Event觸發 workflow 的事件，例如 push、pull_request、schedule、workflow_dispatch（手動按鈕）cron 時間到、git hook
Job一組在同一台機器上執行的 Step。多個 Job 預設平行執行，各自在不同機器上一個 Makefile target
StepJob 裡的一個步驟：執行一行 shell 指令（run），或呼叫一個 Action（uses）script 裡的一行指令
Runner實際執行 Job 的機器。GitHub-hosted 是 GitHub 提供的 VM；self-hosted 是你自己的機器build server
Action別人寫好、可重用的 Step，例如 actions/checkout（下載 repo 原始碼）現成的 library 函式
ArtifactJob 產出並上傳保存的檔案，例如 exe、韌體 image、測試報告，可從網頁下載build 輸出目錄
Secret加密保存的密碼或 API key，在 workflow 裡以變數取用，log 中自動遮蔽不進版控的 .env
Matrix一份 Job 定義展開成多個組合，例如 {gcc, clang} × {ubuntu, windows}巢狀 for 迴圈
Cache跨次執行保存的目錄（例如下載的套件、ccache），加快下次 buildccache
Expression${{ ... }} 語法，讀取 context（分支名、commit SHA、secret 等）或做條件判斷shell 變數展開

理解以下四點，大部分的行為就能推論出來：

  • 設定檔跟著 commit 走。GitHub 讀的是「被 push 的那個 commit」裡的 YAML，所以改 workflow 就是改 code，可以在分支上試，不影響主線。
  • 每個 Job 都是全新、乾淨的 VM。上一次 build 留下的檔案不會存在，同一次執行中不同 Job 之間也不共享檔案系統。要傳遞檔案，用 Artifact 或 Cache。
  • VM 一開始是空的，連你的原始碼都沒有。所以第一個 Step 幾乎都是 actions/checkout，把 repo 抓下來。
  • Step 依序執行，任何一步回傳非 0 的 exit code，Job 就失敗並停止，跟 bash -e 一樣。

GitHub-hosted runner 已預裝大量工具：Ubuntu 有 gcc、clang、make、cmake、python；Windows 有 Visual Studio、MSBuild；macOS 有 Xcode。缺的工具可以在 Step 裡用 apt-get 或 choco 安裝。

第一個 workflow

假設有一個用 Makefile 編譯的 C 專案。以下是最小可用的設定：

.github/workflows/build.yml
name: Build                      # shown in the Actions tab

on:                               # Events that trigger this workflow
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:               # adds a manual "Run workflow" button

jobs:
  build:                           # job id, any name
    runs-on: ubuntu-latest         # which runner VM to use
    steps:
      - uses: actions/checkout@v4   # fetch the repo source

      - name: Compile
        run: make -j"$(nproc)"

      - name: Unit tests
        run: make test

      - name: Upload binary
        uses: actions/upload-artifact@v4
        with:
          name: myapp-linux-x64
          path: build/myapp

怎麼開始用

  1. 把上面的檔案放到 repo 的 .github/workflows/build.yml（路徑必須完全一樣）。
  2. git add、git commit、git push。
  3. 打開 GitHub 上 repo 的 Actions 分頁，會看到一筆執行中的紀錄（黃點），完成後變成綠勾或紅叉。
  4. 點進去選擇 Job，可以展開每個 Step 看完整的 log。
  5. 執行成功時，頁面底部的 Artifacts 區可以下載產出檔（zip 格式）。

YAML 用縮排表示層級，只能用空白、不能用 Tab。縮排錯誤是新手最常見的失敗原因。GitHub 的網頁編輯器會即時檢查語法。

進階功能

Matrix：一次測多種組合

同一份 Job 自動展開成多個組合平行執行。下面這段會產生 2 × 2 = 4 個 Job：

jobs:
  build:
    strategy:
      fail-fast: false              # keep other combos running if one fails
      matrix:
        os: [ubuntu-latest, windows-latest]
        cc: [gcc, clang]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - run: make CC=${{ matrix.cc }}

Job 之間的相依與傳檔

用 needs 讓 Job 依序執行；因為每個 Job 是不同的 VM，檔案要用 artifact 傳過去：

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make
      - uses: actions/upload-artifact@v4
        with: { name: fw, path: build/fw.bin }

  test:
    needs: build                    # start only after build succeeds
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { name: fw }
      - run: ./run-tests.sh fw.bin

Cache：加快重複 build

常用在 ccache 目錄、下載的 toolchain 或套件。key 一樣就還原舊的內容：

      - uses: actions/cache@v4
        with:
          path: ~/.ccache
          key: ccache-${{ runner.os }}-${{ github.sha }}
          restore-keys: ccache-${{ runner.os }}-   # fall back to latest prefix match

排程與條件

on:
  schedule:
    - cron: "0 18 * * *"          # UTC; 18:00 UTC = 02:00 Taiwan time
  push:
    tags: ["v*"]                   # run on version tags such as v1.2.0

jobs:
  release:
    if: startsWith(github.ref, 'refs/tags/v')   # only for tag pushes
    runs-on: ubuntu-latest
    permissions:
      contents: write              # needed to create a release
    steps:
      - uses: actions/checkout@v4
      - run: make release
      - run: gh release create "$GITHUB_REF_NAME" build/*.tar.gz
        env:
          GH_TOKEN: ${{ github.token }}   # auto-provided, no setup needed

Self-hosted runner

在自己的機器上安裝 GitHub 提供的 runner 程式（Linux、Windows、macOS 都有，也支援 ARM），註冊到 repo 後，runs-on: self-hosted 的 Job 就會派到這台機器。適合以下情況：

  • 需要接實體硬體：開發板、JTAG、序列埠。
  • build 很大，例如 Yocto，雲端 runner 的磁碟和時間不夠。
  • 想沿用已經裝好的商用 toolchain 或授權。

設定入口：repo 的 Settings → Actions → Runners → New self-hosted runner，頁面會給出安裝指令。

Embedded 範例：cross-compile 加 QEMU 測試

在 x86 Ubuntu runner 上用 aarch64 toolchain 編譯，再用 qemu-user 直接執行 ARM64 的 unit test 執行檔，不需要開發板：

.github/workflows/arm64.yml
name: ARM64 cross build

on: [push, workflow_dispatch]

jobs:
  cross:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install toolchain and QEMU
        run: |
          sudo apt-get update
          sudo apt-get install -y gcc-aarch64-linux-gnu qemu-user

      - name: Build
        run: make CROSS_COMPILE=aarch64-linux-gnu- -j"$(nproc)"

      - name: Run unit tests under QEMU
        run: |
          # -L points QEMU at the target sysroot for the dynamic loader
          qemu-aarch64 -L /usr/aarch64-linux-gnu ./build/unit_tests

      - uses: actions/upload-artifact@v4
        with:
          name: app-arm64
          path: build/app

多行 shell 用 run: |。每個 run 在 Linux 上預設用 bash -e 執行，任何指令失敗都會讓 Step 失敗。

安全守則

  • Secret 不要寫進 YAML 或程式碼。一律放在 Settings 的 Secrets，以 ${{ secrets.NAME }} 取用。
  • Fork 送來的 PR 拿不到 Secret。這是刻意的設計，避免陌生人改 workflow 把密鑰印出來。不要為了繞過這點而改用 pull_request_target，除非你清楚它的風險。
  • 第三方 Action 鎖定版本。@v4 是會移動的 tag；要求嚴格時改用完整的 commit SHA，例如 actions/checkout@<40 字元 SHA>，避免上游被入侵時跟著中招。
  • 權限最小化。在 workflow 頂層加 permissions: contents: read，只在需要的 Job 開 write。
  • public repo 不要掛 self-hosted runner。任何人送的 PR 都可能在你的機器上執行程式碼。

疑難排解

症狀常見原因處理
push 後完全沒有執行紀錄fork 出來的 repo 預設停用 Actions；YAML 路徑不對；on: 的分支條件沒有包含這個分支到 Actions 分頁啟用；確認檔案在 .github/workflows/；檢查 branches
顯示 “Invalid workflow file”YAML 縮排或語法錯誤點進錯誤訊息會指出行號；用 Tab 縮排是常見原因
Job 一直 “Waiting for a runner”runs-on 的 label 打錯，或 self-hosted runner 離線確認 label 名稱；檢查 runner 狀態
本機可以 build，CI 失敗CI 是乾淨環境，缺少你本機手動裝過的套件，或依賴某個本機路徑在 workflow 裡明確安裝相依套件；這正是 CI 幫你抓到的問題
log 資訊不夠預設只顯示一般輸出Re-run 時勾選 Enable debug logging
想在 runner 上互動除錯VM 執行結束就銷毀在 Step 裡多印資訊，或把中間檔案上傳成 artifact 下載回來看

官方 Action 的主版本號（例如 @v4）會隨時間更新。新專案開始時，到 GitHub Marketplace 確認 actions/checkout、actions/upload-artifact 等的最新主版本。
